# PocketOS SD and GitHub test updater

The updater is intentionally an SD package staging tool, not an R1 flash installer. It writes only beneath the already-mounted microSD (/mnt/sd_0/PocketOS-updates); it never creates mounts, replaces the rootfs, executes payloads or writes bootloader/recovery/flash partitions. Default channel is test. A trusted release verification public key must be provisioned in /etc/pocketos/update-public.pem independently of downloads. A corresponding private release key must stay outside the repo. Neither production signing key nor target dependencies have been provisioned.

On a development machine with Python 3.11+ and OpenSSL, use apps/pack-update.py --sequence N --key /secure/private.pem --output release-folder FILES. Use increasing integer sequences. Package names must start pocketos- or data-. For SD copy the folder onto the card, then run pocketos-update sd /mnt/sd_0/release-folder. For GitHub publish the flat files, including manifest and manifest.sig, as release assets under test-N or test-latest and use pocketos-update github test-N (or test-latest). The fixed repository is lilblock1/PocketOS; HTTPS only, no tokens. The updater requires OpenSSL, sha256sum, standard BusyBox utilities and curl with HTTPS/CA trust for GitHub. A normal foundation currently does not establish those dependencies.

Signatures verify before payload downloads; every payload is checked for digest and exact size, and SD free space is checked with a 16 MiB reserve. Versions are staged in separate directories; selection is atomically renamed with the high-water sequence, so failed staging keeps the former selection. pocketos-update status prints current/previous/high-water; pocketos-update rollback re-verifies and selects the previous package. This is logical selection only, not application activation; FAT power-loss behavior and actual mount mapping must be tested. A stale lock after power interruption requires manual inspection before removal. No automatic pruning, no application launcher consuming selection, no automatic GitHub assets or initial flash image yet. The UI Updates screen currently explains both sources, not an interactive installer.

CI uses ephemeral signing keys to test signed package staging, tampering, replay rejection and rollback. No production key or signed release is generated.

## Phase 3G: interactive signed staging
Settings > Updates now presents GitHub test-latest, microSD inbox and confirmed rollback. With --allow-updates, tapping a source starts one bounded child with a fixed argument list; the UI displays manifest and per-file verification milestones (not live byte percentages), selected/previous versions and errors. Status is read-only and can refresh without the flag. No auto-check, no persistent poller, no credentials, no arbitrary path from UI, and the progress screen prevents navigating away until completion or a 30-minute deadline. Copy a signed release folder's contents to /mnt/sd_0/PocketOS-inbox for local staging. The updater changes its working directory into the card before using relative staging paths, reducing the unmount fallback risk; physical removal during transfer is unsupported. An interruption may leave a stale lock; inspect before cleanup. Existing 16 MiB SD reserve, version checks and signature/digest validation remain. No internal flash update, package execution, boot activation or automatic release publishing: trust key, runtime curl/OpenSSL/CA, actual MIPS SDK and trusted launcher still require provisioning. Rollback restores a staged selection, not physical firmware. Test fixtures generate temporary RSA keys, test structured progress/selection, fixed inbox and replay rejection. No production signing secret is created.

## Phase 5 — real transfer progress and boot identity
The native updater now reports `POCKETOS BYTES transferred total` from the actual growing staging file, once per second while copying/downloading. The denominator is the signed manifest's total payload bytes, not an HTTP header or file count. `POCKETOS PHASE` distinguishes manifest, download/copy, checksum verification, saving, and done. The overall staging bar reserves 15–80% for transfer and reaches 100% only after the verified selection is saved. The R1's small `pocketos-stat -c %s` helper reads regular-file size without rescanning payload data. The screen labels completion as staged, not installed. Existing signature, exact-size, checksum, free-space, high-water, and selection checks remain. Verification and syncing report phase milestones, not real-time hashing or flash percentages. New first-boot preparations stamp a random 16-hex-digit `BUILD_ID` into the read-only rootfs release metadata and candidate report; the shell System screen exposes that ID and the UPT report carries it when supplied. Compare it with the candidate report after boot (ADB `cat /etc/pocketos-release`); it is not an automatic install receipt or a cryptographic proof of flashed contents.

Stock recovery remains a separate unresolved display path. Offline evidence from the extracted vendor `ota_local_method.sh` shows `local_on_ota_data_processed` calculates percentages and calls `local_ota_cb process $n`, which executes the optional `OTA_CB_APP` only when set. `local_ota_update.sh` invokes progress after waiting for chunk `.done` files; those files indicate consumption by the provider pipeline, not verified NAND persistence. The inert recovery executable contains references to `/dev/fb0`, the update script, chunk markers, and `upgrading process %d%%`. The actual recovery invocation environment, renderer and progress callback registration have not been observed; a missing callback is a hypothesis, not a diagnosis. Preserve stock recovery, kernel and flash writer; do not create a second UI that claims to monitor flash across reboot without a proven recovery transport. Next physical investigation should capture the recovery log/serial output and compare the expected BUILD_ID after reboot. No device writes or flash-image builds were performed by this change.

## Phase 5 — independent signed update staging
The startup supervisor accepts a separate read-only rootfs approval file
`/etc/pocketos/update-enable` containing `POCKETOS-R1-UPDATES-1` plus a
parseable, independently provisioned release public key. Production marker owner/mode
must be root 0400 or 0600; public key must be root 0400 or 0444.
Missing approval, missing dependencies or invalid key leaves the UI locked without
stopping startup. The staging helper repeats its approval and key checks and
requires the verified writable, protected vfat microSD mount. Read-only status
remains available. Test fixtures use throwaway keys only.

On a trusted host, `tools/pack-r1-firmware-update.py --rootfs ROOTFS --candidate REPORT --key PRIVATE --sequence N --output NEW_DIR` builds the existing rootfs-only UPT and signs it together with its generated report using the existing manifest format. It never accepts an arbitrary UPT, publishes assets, writes flash, or certifies cold boot. The private key must remain outside the repository. The signed release assets can be staged from the fixed microSD inbox or the test GitHub channel after independent trust provisioning. No automatic installation, boot-selection write, recovery modification, or firmware rollback is implemented by this change. The current preview is not retroactively enabled. Native execution, trust provisioning, actual recovery handoff and cold-boot validation are pending.

## Stable and pre-release channels
The Updates page lists Stable first and Test / pre-release separately. Stable uses the fixed GitHub latest stable release asset endpoint; test uses the fixed test-latest tag. Signed manifests explicitly name stable or test; online channel mismatch is rejected. Both channels share a single increasing staging sequence and high-water mark; publishing a new stable after a test requires a larger sequence. A check fetches only manifest and signature, changes no selection and offers a download only when the signed sequence exceeds staged history. This does not compare installed firmware versions yet. Download confirmation binds the expected sequence and checks signature/channel again. No background checks, automatic channel fallback, installation or key provisioning. Both packers accept --channel stable or test (legacy default test). Publish stable assets only to a non-draft non-prerelease release marked latest; test assets to the designated test-latest tag. No stable assets currently provisioned by this change. Added fixture coverage for channel mismatch, metadata-only check, changed sequence and replay; execution remains pending.

### Firmware-specific manifests and installed sequence
Production staging now requires POCKETOS-R1-FW-1, with precisely the signed R1 UPT and build report; old generic package manifests remain fixture-only. A dedicated flag in the packer produces this format; the reviewed rootfs wrapper uses it. Production compares the signed sequence against both read-only installed UPDATE_SEQUENCE and staged high-water history, failing closed if installed identity is absent. The final candidate preparation must stamp the installed sequence (matching its release) and independently provision the public key. This is a staging boundary, not a parser for the UPT filesystem or an installer; recovery handoff remains blocked. Existing Sonix-Books firmware.c calls /usr/bin/bootmode.sh Recovery after clean storage release; PocketOS does not have this helper. Do not recreate an unverified raw flash write from the comment in that source. New tests are not yet executed.

### Offline trust provisioning
For a fresh reviewed offline candidate only, run `sudo python3 tools/provision-r1-update-trust.py ROOT PUBLIC_PEM SEQUENCE` before compressing and reporting the rootfs. The provisioner refuses the host root, mounted candidate trees, private keys and existing trust. The signing wrapper checks the actual compressed rootfs sequence, approval marker and embedded key against the signer. No private key is added to source, CI, firmware or SD. Neither script enables recovery. No production key or package was generated; new checks still require testing.

### Guarded recovery entry (development, not enabled)
Recovered original bootmode.sh from the pre-firstboot primary squashfs (SHA256 e6a5c0f15abc8e6ca10886a3c1783b5989436604c263451611651897c509593a). It erases the first block of mtd5 and writes a 256-byte space-padded ota:kernel2 flag. The backup contains ota:kernel with FF padding and unrelated theme data in the second eraseblock. New native helper checks exact NAND geometry, good first block and entire expected primary block; only the first block is erased and written, with full readback. This is new code, not the vendor binary, and requires physical validation. The install action requires a separately provisioned root-owned 0400 recovery-enable marker, original kernel/recovery partition digests, newer selected signed firmware, a 50% battery, valid protected SD, verified r1.upt copy, and clean unmount before arming. Unknown existing r1.upt is never overwritten. No write occurs on fixture path. No marker is shipped, no device writes or reboot performed. Recovery writes and userdata preservation still require controlled physical testing; do not call this a finished OTA implementation.

A later install preserves a different pre-existing r1.upt in a unique recovery-backup directory on the inserted microSD, after the new copy verifies. Nothing is automatically deleted. If interrupted before the rename, the recovery flag has not been armed. The final file is rehashed before unmount. This closes the repeated-card-removal issue for leftover manual packages; it remains untested on hardware.
