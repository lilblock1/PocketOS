# Phase 3E: native radio controls
The radio pages and Control Center provide Wi-Fi scan/list, explicit selection, masked ASCII password keyboard (lower/upper/symbols), open or WPA-PSK association and disconnect/status; Bluetooth discover/list, explicit pair/connect/disconnect and adapter status. Wi-Fi uses the existing local wpa_supplicant control socket helper and a fixed four-second wait before retrieving cached scan results. No confirmation of scan completion, DHCP or internet availability. SSIDs are restricted to printable ASCII and supported wpa escape sequences; enterprise/WPA3-only networks are not supported. Password enters child through a pipe, not argv or disk, and UI buffer is wiped after submit or cancel. No password persistence by PocketOS; supplicant runtime retains network config. Bluetooth uses existing BlueZ bluetoothctl, bounded discovery and stop attempts, no automatic trust. Pairing requiring PIN/agent confirmation, audio routing, daemon and driver startup, adapter power switching, and real R1 hardware verification remain pending. Scan only on request; no background scan daemon or persistent radio polling. While a child is outstanding the shell checks at 200 ms, bounded output (16 KiB), 45-second deadline, no dynamic shell interpolation, and explicit --allow-radio for mutating actions. Existing radio services must be installed and running independently. Tests cover parsing, dedup, selection, password buffer wipe, gate and previews. Existing mock supplicant tests are retained. No foundation rebuild or flash.

## Phase 6 development: automatic radio standby

A new portable `pocketos-radio-idle.h` policy computes **recommendations only**, after five continuous minutes of confirmed inactivity. It treats unknown connection state as active for safety. Wi-Fi is a standby candidate only if its association is positively confirmed inactive. Bluetooth is a standby candidate only if all device connections are positively confirmed inactive and Bluetooth audio is not playing. Both are protected while the updater, file/network transfer, radio control job, discovery, or an external radio lease is active. The corresponding radio page protects its adapter. The timer uses elapsed monotonic milliseconds and is reset by any activity; tests include boundary timing, active links, unknown state, transfer/update activity, and output playback.

**Not activated on the player yet:** the existing UI knows adapter *presence*, not connection status, and there is no verified R1-specific safe power-off and wake sequence. No radio is powered down by this change. Implement an opt-in service only after verifying an authoritative Wi-Fi association and Bluetooth client observer, the system owner of each adapter, automatic power-on before GitHub update/connection attempts, and compatible power controls on the device. Keep an explicit user override to leave the radios on. Simply stopping scanning is not equivalent to powering off a radio, and powering down a radio may not materially reduce RAM until its services release allocations. Do not claim measured battery or memory savings without R1 measurements.

### Phase 6: state tracking and read-only connection discovery

The opt-in `pocketos-radio-observe` helper reports `wifi=active|idle|unknown` and `bluetooth=active|idle|unknown` without revealing SSIDs, MAC addresses, IP addresses or connection names. It queries the already-running wpa_supplicant and BlueZ clients; it does **not** power radios or start their services. Wi-Fi considers authentication, association, scanning and completed association active; only an authoritative `DISCONNECTED` or `INACTIVE` is tentatively idle. BlueZ must support `bluetoothctl devices Connected` and return successfully with an empty device list to be considered idle. Unknown/error responses are never idle. This observation does not establish whether network sockets or app downloads are in use, so the caller must independently hold an activity lease for transfers.

The radio policy now has a monotonic consecutive-idle tracker that resets each affected timer on activity, unknown observations, updates, discovery, manual radio operations, and clock rollback. The five-minute threshold begins at the first positively idle observation; a new connection or job clears the accumulated idle duration. Unit tests and mock-client fixtures are included in the application workflow.

**Not yet enabled:** full-shell automatic management and power transitions. The development helper and policy need a hardware-verified radio power/wake backend and proof that updates and streaming applications hold leases. The UI's adapter-presence checks are insufficient to activate auto-sleep. To minimize RAM safely, benchmark existing daemon memory, scan behavior, and idle CPU before deciding whether BlueZ/wpa_supplicant should stop or remain resident; merely turning radio power off might not free daemon RAM.
